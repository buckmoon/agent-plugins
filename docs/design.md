# reader-first の設計

この文書は、reader-first のスキルと試し読みフックが、なぜ今の形になっているかを説明する。スキルやフックの振る舞いを変える前に読み、変えてよいかを判断する材料にしてほしい。版 0.1.0（2026年9月）時点の内容で、下の数字はどれも小さな実験から出たものである。入れ方は [install-claude.md](install-claude.md) と [install-codex.md](install-codex.md)、ログと費用は [privacy-and-cost.md](privacy-and-cost.md) にある。

## 解きたい問題

AIが書いた報告は、書いたAIにとっては分かりやすくても、読み手には読みにくいことが多い。AIは作業中に多くのファイルやツールの出力を見ていて、読み手が見ていない語や出来事を、説明なしに使ってしまうからである。読み手は読み終えても、自分が次に何をすればよいか分からない。

## 考え方：読み手の手持ちと次の行動

スキルは、書き始める前に二つを決めさせる。

- **読み手の手持ち**：読み手は誰で、これまでに何を見てきたか
- **次の行動**：読み終えた直後に、読み手に何をしてほしいか

冒頭に次の行動を書き、本文は手持ちの範囲の言葉で書き、読み手が短く返せる問いで終える。この二つを決めずに書き方の規則だけを足しても、何を削ってよいかの基準がないので、文章はかえって長くなる。

## 試し読み：読み手が見たものだけを持った別のAIに読ませる

書き手のAIは、自分の文章を読み手の立場で読み直すことが苦手である。作業の文脈を持っているほど、読み手が知らない語に気づきにくい。そこでフックは、下書きを出す前に、読み手が見たものだけを渡した別のAIに読ませる。このAIを「試し読み役」と呼ぶ。

試し読み役が答えるのは二つである。

1. 読み終えた直後に、読み手は何をすればよいか分かるか
2. 読み手が引っかかる文と、そこで書き手に返したい質問（多くても5つ）

どちらかに問題があれば、フックは書き込みや投稿を止め、質問を書き手のAIに返す。

試し読み役は、利用者が使っているAIのコマンドを、フックから1回呼び出して動かす。Claude Code では `claude -p`、Codex では `codex exec` を使う。モデルは、Claude Code では利用者の既定のもの、Codex では Codex の既定のもの（利用者の config.toml の設定は使わない）で、環境変数 `COLD_READ_GATE_MODEL` にモデル名を入れると変えられる。だから、試し読みの利用量は利用者自身のアカウントから減る。

### 読み手の種類

試し読み役に渡すものは、読み手によって変わる。読み手は、下書きのファイル名の先頭で指定する。

| ファイル名の先頭 | 読み手 | 試し読み役に渡すもの |
|---|---|---|
| なし（例：`20260925-1430.md`） | 依頼者（AIに作業を頼んでいる人） | 依頼者の発言と、画面に出たAIの本文。ツールの入出力や、作業中に読んだファイルは渡さない |
| `github-` | issue やPRの読み手 | 下書きの本文だけ |
| `slack-` | Slack の読み手（社外の人も含む） | 下書きの本文だけ |
| `email-` | メールの受け手 | 下書きの本文だけ |
| `doc-` | 後日その文書を開く人 | 下書きの本文だけ |

依頼者以外の読み手は、AIと依頼者のやり取りを見ていないので、本文だけを渡す。下書きを置く場所と書き方は、スキルの [drafts.md](../plugins/reader-first/skills/reader-first/drafts.md) にある。

## 直すのは元の書き手

試し読みの結果は、読み手の人間には渡さず、書いたAIに返して直させる。文脈を持たない別のAIに書き直させる方法も試したが、次の二つの理由で採らなかった。

- **外から書き直しても短くならない。** 書き直し役は何を捨ててよいか判断できないので、言い換えて説明を足す方向に傾く。
- **外から書き直すと、用件を取り違える。** 実際には読み手が実機で確認を再開する段階だったのに、書き直し役は冒頭に「知っておくだけでよい」と書いた。後の節で読み比べてもらった人間の読み手は、この版で次の一手が分かる確信度を5段階の1と答えた。

また、本当に足りない情報（「残った確認を誰がいつするか」など）は、作業の文脈を持つ元の書き手にしか答えられなかった。

## 実験で分かったこと

作者の手元にあった作業報告15本（108文）で試した。どの文が読み手にとって重いか（引っかかる、読み直す、そのままでは次に動けない）は、事前に別のAIが読み手の立場で判定した。試し読み役は、同じ指示と同じ入力で2回、互いに独立に動かし、判定がどれだけぶれるかも見た。今のフックが動かすのは、このうち1回分にあたる。

| 方法 | 重い文を拾えた割合 | 指摘が当たっていた割合 |
|---|--:|--:|
| 記録にない珍しい語を機械で拾う | 31% | 65% |
| 試し読み役（1回目と2回目） | 52〜60% | 73〜78% |

2回の判定は、91%の文で一致した。試し読み役は、読み手が見ていない出来事を指す文に強く、一文に情報を詰め込みすぎた文には弱かった。

次の一手が分かる確信度（5段階）は、元の報告が2.7〜2.8、試し読みの質問を使って次の行動を冒頭に置いた版が4.3〜4.5だった（AIによる評価）。読み手の人間1人に6本を読み比べてもらうと、確信度は2.8から4.2に上がった。ただし、読みやすさの順位の差はAIの評価ほど大きくなく、短い元の報告を1位に選んだこともあった。そこでスキルは、数行で済む判断の要らない返事には手順を当てはめず、そのまま短く書かせる。

## 止めるのは1回だけ

フックが止めるのは、同じ依頼の中で読み手の種類ごとに1回だけである。「同じ依頼」は、依頼者の最後の発言で区切る。依頼者が新しいメッセージを送ると、また1回止められるようになる。1回だけにした理由は三つある。

- **止めすぎる。** 過去の報告3本に当てると、3本とも止める判定になった。質問には、重要でないものも混じっていた。
- **答えられない質問がある。** 書き手にも分からないことは、何度聞かれても答えられない。そうした質問は「まだ分かっていないこと」として本文に残させる。
- **待ち時間と利用量がかかる。** 試し読みは1回に数秒から数十秒かかる。

試し読み役の呼び出しに失敗したときも、止めずに通す。試し読みは、書き込みや投稿を止めてまで守るべき安全装置ではないからである。

## 出る前に止める

最初の試作は、AIが応答を書き終えたときに動くフックで試し読みしていた。しかしそれでは、依頼者は最初の版と直した版の両方を目にする。そこで今は、長い報告（400字以上）をいったん下書きファイルに書かせ、その書き込みの直前に試し読みする。GitHub の issue やPRへの投稿も、投稿の直前に読む。Slack やメールは、下書きファイルに書くときだけ読み、実際に送るときには読まない。400字より短い下書きや投稿は読まない。

## 採らなかった方向

- **読み手に、知っていることを申告させる。** 相手が何を伝えてくるか分からないまま、自分の知識を書き出すことはできない。
- **読み手の像をプロンプトで細かく指定する。** 先行研究では、指定しても狙った読みやすさにはあまりならなかった（Rooein ほか 2023）。
- **知らない語を機械で拾うだけにする。** 重い文の3分の1しか拾えなかった。
- **知らない語にマウスを重ねると定義を出す。** 専門語による読みにくさは和らがなかった（Shulman ほか 2020）。

## まだ分かっていないこと

- **人間の読み手による確認が少ない。** 重い文の判定・試し読み・評価はほぼAIで行い、人間の読み比べは1人・6本だけである。
- **既知のことを説明しすぎる文は試していない。** 実験は、知らない語と、読み手が見ていない出来事の指し示しだけを測った。
- **スキルが呼ばれないことが多い。** フックは、AIが応答を書き終えるたびに、依頼者への400字以上の報告が、最後に書いた依頼者向けの下書きと同じ内容だったかをログに記録している（止めはしない）。作者の手元の記録では、34件中2件しか下書きを通っていなかった。ログの場所は privacy-and-cost.md にある。
- **一部の投稿経路は読まない。** GitHub への投稿は、GitHub の MCP の道具を使ったときだけ読む。`gh` コマンドで投稿したときは読まない。Codex では、既存の下書きの書き換えも読まない（全文がフックに渡らないため）。
- **会話が長くなって圧縮されたあとの記録を渡していない。** 圧縮後の要約を試し読み役に渡さないので、依頼者が前に見た語を「知らない語」と誤って判定する可能性がある。
