# 読み手を先に決めて書く

書き始める前に、次の二つを決める。以下の手順は、すべてこの二つから出てくる。迷ったらここに戻る。

- **読み手の手持ち**：読み手は誰で、これまでに何を見てきたか
- **次の行動**：読み終えた直後に、読み手に何をしてほしいか

## 手順

1. **読み手を決める。** [readers.md](readers.md) から読み手の種類を選び、その手持ちを確かめる。
2. **次の行動を一つ決める。** 返事をする、選ぶ、操作する、レビューする、手順を実行する、知っておくだけ、などから選ぶ。行動がいくつもあるときは、読み手が最初に取る一つにする。
3. **冒頭に次の行動を書く。** 読み手が最初の数行で「自分は何をすればよいか」を知れるようにする。書き方の例は readers.md の各読み手の行にある。
4. **手持ちの範囲の言葉で本文を書く。** 読み手が見ていないファイル名、関数名、エラーコード、作業中に付けた呼び名（「案A」など）、issue番号は、一般的な言葉に言い換えるか、その場で一言説明する。本文は役割ごとに段落を分ける。役割は、起きたこと・分かったこと、まだ分かっていないこと（誰がいつ確かめるかも書く）、次の提案の三つで、要らない段落は書かない。段落の中は「なぜ・だから・ただし」でつなぐ。
5. **次の行動を求めて終える。** 返事がほしい相手には、「はい」か短い一言で返せる問いで終える。選んでほしいときは、選択肢を本文の中に並べる。
6. **下書きを通すか決める。** 次のどれかに当たるなら、[drafts.md](drafts.md) の手順で下書きを書き、試し読みに通す。
   - 依頼者を長く待たせた報告：作業をやり終えた、調査した、道具を10回以上使った、判断や操作を頼む
   - 依頼者が第三者に渡す文面
   - ファイルとして残す文書

   依頼者との短いやり取りは、下書きを通さずにそのまま書く。

**完了条件**：読み手が、手持ちの情報だけで、次に何をすればよいかが分かる。冒頭を読めば何をすべきか分かり、読み手の知らない語が説明なしに残っていない。版を重ねた文章なら、前の版との違いや直した理由が本文に残っていない。

## 短い返事

数行で済み、判断の要らない返事は、手順1と2を頭の中で済ませて短く書く。短さそのものが「深く読まなくてよい」という合図になる。

## 版を重ねるとき

依頼者と相談しながら同じ文章を何度も直すとき、依頼者はすべての版を見ているが、読み手が読むのは最新の版だけである。前の版は読み手の手持ちにない。だから最新の版の本文には、その版の内容だけを書き、次のような版の経緯は書かない。

- 前の版との違い（「初版では〜としていたが」「今回〜を足した」）
- 直した理由（「ご指摘を受けて」「分かりにくいという声があったので」）
- 直す前の言い回しや、採らなかった案

経緯は、依頼者への返事の中で、本文とは分けて「変えた点」として伝える。後に残す必要があれば、変更履歴やコミットの説明に書く。

ただし、読み手がすでに前の版を読んでいるとき（配った文書の改訂版を配り直す、レビュー済みの PR を直すなど）は、前の版が読み手の手持ちに入っている。このときは、前の版から何が変わったかを冒頭に短く書く。直した理由は、読み手の判断に要る分だけにする。

## 書式との分担

このスキルが決めるのは、何をどの順で書くかである。見出しやコードフェンスなどの書式を決める別のスキルや決まりがあれば、書式はそちらに従う。

## 試し読み（フック）

このプラグインのフックが、下書きへの書き込みと GitHub への投稿（400字以上）の直前に、読み手の立場の別のAIに文章を読ませる。読み手は下書きのファイル名の先頭で決まる。引っかかる点があれば1回だけ止めて質問を返すので、答えられる質問には本文で答え、答えられない質問は「まだ分かっていないこと」として本文に残す。
